# Odolog — план разработки

## Контекст

Замена связки Telegram + Google Sheets для учёта пробега и расхода топлива.
Записи двух типов: показание одометра (раз в день) и заправка (когда мигает лампочка).

---

## Стек

| Слой | Технология |
|------|------------|
| Frontend | React + Vite + TypeScript + Tailwind CSS |
| Offline DB | Dexie.js (IndexedDB) |
| Backend | Node.js + Express + SQLite (better-sqlite3), отдаёт и API, и статику фронта |
| Auth | JWT Bearer |
| PWA | vite-plugin-pwa |

---

## Схема данных

```ts
// vehicles
{ id: string, name: string }

// odometerEntries
{ id: string, vehicleId: string, date: string, odometer: number, synced: boolean, updatedAt: number, deletedAt: number | null }

// fuelEntries
{ id: string, vehicleId: string, date: string, odometer: number, liters: number, totalCost: number, synced: boolean, updatedAt: number, deletedAt: number | null }
```

- `id` — nanoid, генерируется на клиенте (записи — 21 симв, машины — 6 симв для URL)
- `date` — ISO строка (YYYY-MM-DD), по умолчанию сегодня, редактируемая
- `synced` — флаг локальной синхронизации
- `updatedAt` — timestamp (ms), при конфликте побеждает большее значение
- `deletedAt` — timestamp (ms) мягкого удаления, `null` если запись активна

Вычисляемые поля (не хранятся): пробег между записями, расход л/100км, цена за литр.

---

## Синхронизация

Двусторонняя, сервер — источник истины.

1. Push: отправляем все записи где `synced = false`
2. Pull: тянем с сервера все записи новее `lastSyncAt`
3. Конфликт по одному `id`: побеждает запись с бо́льшим `updatedAt`
4. Авто-sync при появлении сети + кнопка ручного sync

## Архитектура

### Frontend — Feature-Sliced Design (FSD)
```
src/
  app/        # провайдеры, роутинг, глобальные стили
  pages/      # страницы
  widgets/    # составные блоки UI
  features/   # фичи (add-odometer-entry, add-fuel-entry, sync)
  entities/   # сущности (vehicle, odometer-entry, fuel-entry)
  shared/     # lib (db, api-client), ui (компоненты), types
```

### Backend — Onion Architecture
```
src/
  domain/         # сущности + интерфейсы репозиториев (чистый TS, без зависимостей)
  application/    # use cases (бизнес-логика)
  infrastructure/ # реализация репозиториев (SQLite), Express роуты, JWT
```

## UI

### Навигация

- **Таббар снизу**: Записи / Аналитика / Настройки
  - Аналитика появляется в фазе 4, Настройки — в фазе 5
- **FAB** (кнопка "+") на экране Записей: при тапе раскрывается speed-dial с двумя вариантами — "Одометр" и "Заправка" (иконка + подпись; иконки подобрать при реализации)

### Экран Записей

- **Шапка**: имя автомобиля + "Последняя запись: [дата]"
- **Навигация по месяцам**: `< Май 2026 · N записей >` — переключение стрелками или свайпом влево/вправо
- По умолчанию — текущий месяц (даже если пустой)
- **Список**: оба типа вперемешку, сортировка по дате убывающая (новые сверху)
  - Odometer entry: синяя иконка + "124 350 км" + дата
  - Fuel entry: зелёная иконка + "45 л · 3 150 ₽" + дата
  - Тап по карточке в фазе 1 ничего не делает (редактирование — фаза 5)

### Стабы пустого состояния

- **Глобальный стаб** (нет ни одной записи у машины; дизайн `docs/ui-examples/global-stub.png`):
  - Шапка: имя авто + "Записей пока нет" (без даты последней записи)
  - Навигация по месяцам скрыта
  - Карточка по центру: иконка + "Начните вести учёт" + подпись "Записывайте показания одометра и заправки — приложение само посчитает расход и пробег"
  - Две кнопки внутри карточки: "Одометр" / "Заправка" (открывают те же bottom sheet, что и FAB)
- **Стаб пустого месяца** (записи есть, но не в текущем выбранном месяце; дизайн `docs/ui-examples/month-stub.png`):
  - Шапка и навигация по месяцам отображаются как обычно (`· 0 записей`)
  - По центру: иконка + "Нет записей за этот месяц" + подпись "Выберите другой месяц или добавьте новую запись"
  - Кнопка-ссылка "Последняя запись: [дата] →" — переход к месяцу с последней записью

### Bottom sheet — форма одометра

- Заголовок: "Одометр"
- Поле даты: нативный `<input type="date">`, отображается как "Сегодня, 30 мая" *(открытый вопрос: нативный пикер vs кастомный)*
- Поле "Показание одометра" (км)
- Дельта в реальном времени под полем:
  - положительная → зелёная "↑ +260 км с последней записи"
  - отрицательная → красная "↓ −1 350 км — проверьте значение"
  - сохранение не блокируется при отрицательной дельте
- Кнопка "Сохранить"

### Bottom sheet — форма заправки

- Заголовок: "Заправка"
- Поле даты (то же, что в форме одометра)
- Поля в двух колонках: "Одометр" (км) + "Литры" (л)
- Дельта одометра — аналогично форме одометра
- Поле "Общая стоимость" (₽), во всю ширину
- Вычисляемое поле в реальном времени: "Цена за литр: 70 ₽" (стоимость ÷ литры)
- Кнопка "Сохранить"

### После сохранения

- Успех: bottom sheet закрывается, новая запись появляется в списке с анимацией
- Ошибка: тост с текстом ошибки + кнопка "Повтор"
- Нет сети (фаза 3): информационный тост "Нет сети — запись сохранена локально"

### Фаза 2 — Backend
*Цель: API с авторизацией, данные хранятся на сервере*

- [ ] **Проект: Express + better-sqlite3 + Onion-скелет**
  - [ ] Структура `domain / application / infrastructure` создана; `domain` не импортирует ничего из внешних слоёв
  - [ ] Сервер стартует, `GET /api/health` возвращает 200
  - [ ] Схема SQLite создаётся при первом запуске: `vehicles`, `odometerEntries`, `fuelEntries` — поля совпадают с клиентской схемой (включая `updatedAt`, `deletedAt`)
  - [ ] Повторный запуск сервера не пересоздаёт таблицы и не теряет данные
  - [ ] Конфиг (порт, путь к БД, JWT-секрет) читается из env

- [ ] **Статика + SPA fallback**
  - [ ] Express отдаёт собранный `dist` фронта
  - [ ] Прямой заход на любой клиентский роут (например `/analytics`) возвращает `index.html`, а не 404
  - [ ] Fallback не перехватывает запросы к `/api/*` — несуществующий API-роут возвращает 404 (JSON), а не HTML

- [ ] **`POST /auth/login` → JWT**
  - [ ] Верные креды (из env) → 200 + токен; неверные → 401
  - [ ] Токен содержит срок жизни (`exp`)
  - [ ] JWT-секрет не захардкожен в коде

- [ ] **JWT middleware**
  - [ ] Запрос без токена, с невалидным или просроченным токеном → 401 (JSON-ошибка)
  - [ ] Валидный токен → запрос проходит к роуту
  - [ ] `/auth/login`, `/api/health` и статика не требуют токена

- [ ] **CRUD `odometerEntries`**
  - [ ] `PUT /api/odometer-entries/:id` — upsert: принимает клиентский `id` (nanoid), создаёт или обновляет запись
  - [ ] `GET /api/odometer-entries?vehicleId=...&since=...` — фильтр по `updatedAt > since` (задел под pull в фазе 3); без `since` отдаёт всё
  - [ ] `DELETE /api/odometer-entries/:id` — мягкое удаление: проставляет `deletedAt`, физически запись не удаляется
  - [ ] Валидация: `odometer > 0`, `date` в формате `YYYY-MM-DD`, `vehicleId` существует → иначе 400 с текстом ошибки
  - [ ] Бизнес-логика лежит в use cases (`application`), роуты — тонкие обёртки

- [ ] **CRUD `fuelEntries`**
  - [ ] Те же критерии, что и для `odometerEntries` (upsert, `since`-фильтр, soft delete)
  - [ ] Дополнительная валидация: `liters > 0`, `totalCost > 0`
