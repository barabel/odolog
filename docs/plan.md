# Odolog — план разработки

## Контекст

Замена связки Telegram + Google Sheets для учёта пробега и расхода топлива.
Единая сущность Entry с полем `type`: показание одометра (`odometer`) или заправка (`fuel`).

---

## Стек

| Слой | Технология |
|------|------------|
| Frontend | React + Vite + TypeScript + Tailwind CSS |
| Offline DB | Dexie.js (IndexedDB) |
| Backend | Node.js + Express + SQLite (better-sqlite3), отдаёт и API, и статику фронта |
| Auth | JWT Bearer |
| PWA | vite-plugin-pwa |

## Схема данных

Одна таблица `entries` — discriminated union по `type`.
Заправка = надмножество показания одометра, поэтому показания живут на одном таймлайне.

```ts
// vehicles
{ id: string, name: string }

// entries — discriminated union по type
type EntryBase = {
  id: string
  vehicleId: string
  measuredAt: number   // момент измерения, задаёт пользователь
  odometer: number
  createdAt: number    // момент создания строки, системный, иммутабельный
  updatedAt: number
  deletedAt: number | null
  synced: boolean
}
type OdometerEntry = EntryBase & { type: 'odometer' }
type FuelEntry     = EntryBase & { type: 'fuel'; liters: number; totalCost: number }
type Entry = OdometerEntry | FuelEntry
```

Индекс Dexie: `id, vehicleId, type, measuredAt, synced, deletedAt`.

- `id` — nanoid, генерируется на клиенте (записи — 21 симв, машины — 6 симв для URL)
- `measuredAt` — epoch ms, момент измерения; задаёт пользователь (дата + время, точность до минуты), по умолчанию «сейчас», редактируемый; **по нему строится порядок и считается пробег**. Заменяет прежний `date`
- `createdAt` — epoch ms, момент создания строки; системный, иммутабельный; нужен для тай-брейка при равном `measuredAt` и для аудита (видно записи, внесённые задним числом)
- `synced` — флаг локальной синхронизации
- `updatedAt` — timestamp (ms), при конфликте побеждает большее значение
- `deletedAt` — timestamp (ms) мягкого удаления, `null` если запись активна

---

## Синхронизация

Двусторонняя, сервер — источник истины.

1. Push: отправляем все записи где `synced = false`
2. Pull: тянем с сервера все записи новее `lastSyncAt`
3. Конфликт по одному `id`: побеждает запись с бо́льшим `updatedAt`
4. Авто-sync при появлении сети + кнопка ручного sync

## Архитектура

### Frontend — Feature-Sliced Design (FSD)
```
src/
  app/        # провайдеры, роутинг, глобальные стили
  pages/      # страницы
  widgets/    # составные блоки UI
  features/   # фичи (add-odometer-entry, add-fuel-entry, sync)
  entities/   # сущности (vehicle, entry)
  shared/     # lib (db, api-client), ui (компоненты), types
```

### Backend — Onion Architecture
```
src/
  domain/         # сущности + интерфейсы репозиториев (чистый TS, без зависимостей)
  application/    # use cases (бизнес-логика)
  infrastructure/ # реализация репозиториев (SQLite), Express роуты, JWT
```

## UI

### Навигация

- **Таббар снизу**: Записи / Аналитика / Настройки
  - Все три таба есть с фазы 1; Аналитика и Настройки до фаз 4 и 5 — заглушки
- **FAB** (кнопка "+") на экране Записей: при тапе раскрывается speed-dial с двумя вариантами — "Одометр" и "Заправка" (иконка + подпись; иконки подобрать при реализации)

### Экран Записей

- **Шапка**: имя автомобиля + "Последняя запись: [дата]"
- **Список**: плоский список всех записей, оба типа вперемешку, сортировка по `measuredAt` убывающая (новые сверху), тай-брейк по `createdAt`
  - На этом этапе — первые 50 записей; пагинация и фильтры — в будущем
  - Odometer entry: синяя иконка + "124 350 км" + дата/время
  - Fuel entry: зелёная иконка + "45 л · 3 150 ₽" + дата/время
  - **Открытый вопрос:** невалидная запись (одометр меньше, чем у предыдущей по `measuredAt`) — помечать её визуально в списке или вообще не давать сохранить? Нужна ли пометка в списке, зависит от ответа
  - Тап по карточке в фазе 1 ничего не делает (редактирование — фаза 5)
  - Удаление записи — жестом из списка (мягкое, `deletedAt`)

### Стаб пустого состояния

- **Глобальный стаб** (нет ни одной записи у машины; дизайн `docs/ui-examples/global-stub.png`):
  - Шапка: имя авто + "Записей пока нет" (без даты последней записи)
  - Карточка по центру: иконка + "Начните вести учёт" + подпись "Записывайте показания одометра и заправки — приложение само посчитает расход и пробег"
  - Две кнопки внутри карточки: "Одометр" / "Заправка" (открывают те же попапы, что и FAB)

### Попап — форма одометра

- Заголовок: "Одометр"
- Поле даты + времени (`measuredAt`): тап открывает попап с календарём и выбором времени, по умолчанию «сейчас», допускает прошлое (бэкдейтинг) — решения в `docs/adr/0004-date-time-picker-on-libraries.md`
- Поле "Показание одометра" (км) — числовая клавиатура на мобиле
- Дельта в реальном времени под полем (относительно соседней по `measuredAt` записи):
  - положительная → зелёная "↑ +260 км с последней записи"
  - отрицательная → красная "↓ −1 350 км — проверьте значение"
  - **Открытый вопрос:** блокировать ли сохранение при отрицательной дельте. Изначально задумывалось сохранять и помечать запись невалидной; альтернатива — не давать сохранить вовсе
- Кнопка "Сохранить"

### Попап — форма заправки

- Заголовок: "Заправка"
- Поле даты + времени (то же, что в форме одометра)
- Поля в двух колонках: "Одометр" (км) + "Литры" (л) — числовая клавиатура, литры дробные (десятичный разделитель зависит от локали клавиатуры)
- Дельта одометра — аналогично форме одометра
- Поле "Общая стоимость" (₽), во всю ширину
- Вычисляемое поле в реальном времени: "Цена за литр: 70 ₽" (стоимость ÷ литры)
- Кнопка "Сохранить"

### После сохранения

- Успех: попап закрывается, новая запись появляется в списке с анимацией
- Ошибка записи в IndexedDB в фазе 1 не показывается — тост-механизма нет, случай практически недостижим
- Тосты появляются в фазе 3 вместе с сетевыми ошибками: ошибка + "Повтор", "Нет сети — запись сохранена локально"

### Фаза 2 — Backend
*Цель: API с авторизацией, данные хранятся на сервере*

- [ ] **Проект: Express + better-sqlite3 + Onion-скелет**
  - [ ] Структура `domain / application / infrastructure` создана; `domain` не импортирует ничего из внешних слоёв
  - [ ] Сервер стартует, `GET /api/health` возвращает 200
  - [ ] Схема SQLite создаётся при первом запуске: `vehicles`, `entries` — поля совпадают с клиентской схемой (`type`, `measuredAt`, `createdAt`, `updatedAt`, `deletedAt`; `liters`/`totalCost` nullable, заполняются только при `type='fuel'`)
  - [ ] Повторный запуск сервера не пересоздаёт таблицы и не теряет данные
  - [ ] Конфиг (порт, путь к БД, JWT-секрет) читается из env

- [ ] **Статика + SPA fallback**
  - [ ] Express отдаёт собранный `dist` фронта
  - [ ] Прямой заход на любой клиентский роут (например `/analytics`) возвращает `index.html`, а не 404
  - [ ] Fallback не перехватывает запросы к `/api/*` — несуществующий API-роут возвращает 404 (JSON), а не HTML

- [ ] **`POST /auth/login` → JWT**
  - [ ] Верные креды (из env) → 200 + токен; неверные → 401
  - [ ] Токен содержит срок жизни (`exp`)
  - [ ] JWT-секрет не захардкожен в коде

- [ ] **JWT middleware**
  - [ ] Запрос без токена, с невалидным или просроченным токеном → 401 (JSON-ошибка)
  - [ ] Валидный токен → запрос проходит к роуту
  - [ ] `/auth/login`, `/api/health` и статика не требуют токена

- [ ] **CRUD `entries`**
  - [ ] `PUT /api/entries/:id` — upsert: принимает клиентский `id` (nanoid), создаёт или обновляет запись
  - [ ] `GET /api/entries?vehicleId=...&since=...` — фильтр по `updatedAt > since` (задел под pull в фазе 3); без `since` отдаёт всё
  - [ ] `DELETE /api/entries/:id` — мягкое удаление: проставляет `deletedAt`, физически запись не удаляется
  - [ ] Валидация: `type ∈ {odometer, fuel}`, `odometer > 0`, `measuredAt`/`createdAt` — валидные timestamp, `vehicleId` существует → иначе 400 с текстом ошибки
  - [ ] При `type='fuel'` дополнительно: `liters > 0`, `totalCost > 0`
  - [ ] Бизнес-логика лежит в use cases (`application`), роуты — тонкие обёртки
