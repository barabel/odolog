# Единая таблица `entries` и пользовательское время `measuredAt`

Объединяем `odometerEntries` и `fuelEntries` в одну таблицу `entries` — discriminated union по полю `type: 'odometer' | 'fuel'`. Заодно убираем `date: string` (гранулярность сутки, «одна запись в день») и заменяем на `measuredAt: number` (epoch ms) — момент измерения, который задаёт пользователь (дата + время) и может ставить задним числом. Добавляем `createdAt: number` — системный иммутабельный момент создания строки.

## Почему

- **Заправка — надмножество показания одометра** (`FuelEntry` = `OdometerEntry` + `liters` + `totalCost`), и обе несут показание одометра. При раздельных таблицах показания живут на двух таймлайнах сразу, и для расчёта пробега их всё равно пришлось бы сливать. Одна таблица делает таймлайн одометра цельным из коробки: пробег = разница `odometer` между соседними по `measuredAt` записями любых типов; расход = между записями `type='fuel'`.
- **Discriminated union** убирает главный минус объединения — `liters`/`totalCost` не становятся nullable на уровне типов (они есть только у варианта `fuel`).
- **`measuredAt` вместо `date`**: решение «записывать когда захочешь, в любой момент» требует внутридневного порядка, который суточный `date` дать не может. Порядок и пробег считаются по `measuredAt`.
- **`createdAt` отдельно от `measuredAt`**: момент вставки строки ≠ момент измерения (бэкдейтинг). `createdAt` даёт детерминированный тай-брейк при равном `measuredAt` и бесплатный аудит. `measuredAt` — для бизнес-логики, `createdAt` — системный.

## Рассмотренные альтернативы

- **Раздельные таблицы (как было).** Отвергнуто: дублирование, разорванный таймлайн одометра, расчёт пробега требует слияния на чтении.
- **Один `measuredAt` без `createdAt`.** Отвергнуто: недетерминированный порядок при совпадении времени до минуты → скачущий пробег.
- **Жёсткая валидация монотонности одометра.** Отвергнуто: воюет с осознанно разрешённым бэкдейтингом. Вместо запрета — мягкая пометка: запись с `odometer` меньше, чем у предыдущей по `measuredAt`, сохраняется, но помечается невалидной в UI.

## Границы (расширяемость)

`entries` = «показание одометра в момент времени плюс опциональная нагрузка по `type`». Будущий тип с одометром (ТО, ремонт) — новый вариант union здесь; запись без одометра (страховка, налог) — отдельная таблица, чтобы не делать `odometer` опциональным.

## Следствия

- Миграции нет: формы не реализованы, реальных записей нет — схему переделываем (drop старых таблиц, новая `entries`).
- Sync, backend CRUD и UI работают с одной сущностью `Entry` вместо двух.
